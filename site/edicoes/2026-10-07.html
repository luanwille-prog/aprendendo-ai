Skill é um playbook lido sob demanda

O agente enxerga só um resumo curto de cada skill. Quando julga o conhecimento útil, lê o texto inteiro e injeta no contexto. Essa técnica se chama progressive disclosure (revelação progressiva) e muda o rumo do agente no começo da tarefa.

MCP como camada de distribuição de skills

Em vez de instalar skills em cada máquina, a empresa mantém um servidor MCP remoto como fonte única. Ele aplica política, entrega a melhor versão por papel do usuário e funciona em clientes de chat comuns. Isso ataca os problemas de skills feitas para devs e de clientes sem suporte.

Janela maior esquece o meio

Um agente que monitora uma aplicação puxa logs a cada chamada, e o contexto só cresce. A palestrante diz que aumentar tokens deixou de funcionar: pela curva de atenção, o modelo guarda o começo e o fim e esquece o meio. Dados demais também podem poluir o contexto e abrir espaço para prompt injection.

Quatro estratégias de context engineering

Context engineering (engenharia de contexto) é dar ao modelo a informação certa na hora certa. A palestrante resume em quatro verbos. Externalizar move dados grandes para armazenamento persistente. Selecionar recupera só o relevante. Comprimir resume ou compacta. Isolar separa o contexto entre agentes.

Gerenciadores de conversa no Strands

O Strands Agents oferece três gerenciadores: janela deslizante (guarda só as mensagens recentes), sumarização (resume as antigas) e a combinação dos dois. No exemplo, o agente preserva as quatro últimas mensagens e resume uma proporção do restante, definida em 50%. A criação do agente leva uma linha de código e troca de modelo exige mais uma.

Mais 2 ideias deste talk

Ponteiro de memória para logs grandes

Em vez de colocar logs enormes no contexto, uma ferramenta os grava num armazenamento e devolve só um ID. O ID fica no estado do agente. Se o agente precisar dos logs, outra ferramenta usa o ID para buscá-los. Em um swarm (grupo de agentes), o ponteiro passa pelo estado de invocação e evita que um agente despeje lixo no contexto do outro.

Limite de chamadas e handles assíncronos

Agentes podem repetir a mesma ferramenta sem parar. A solução mostrada é limitar cada ferramenta a três chamadas e devolver respostas claras. Para ferramentas MCP ou APIs lentas, um handle assíncrono permite iniciar o trabalho e consultar o resultado depois, sem estourar o tempo limite de um gateway.

Async handle (handle assíncrono). Um handle assíncrono é como a senha que a lavanderia entrega quando você deixa a roupa: você vai embora, faz outras coisas e volta depois com a senha para buscar o que ficou pronto.

  1. Algumas tarefas demoram, como pedir um relatório a outro sistema. Se o agente fica parado esperando, tudo trava junto com ele.
  2. Num handle assíncrono (async handle, um comprovante de tarefa em andamento), o agente pede o trabalho e recebe na hora só um número de identificação, sem esperar o resultado.
  3. Com esse número, o agente segue a conversa e, mais tarde, pergunta se a tarefa terminou. Quando terminar, ele busca o resultado.
  4. Isso evita o tempo limite (timeout) de intermediários como o API Gateway da AWS, que corta a chamada se a resposta demora demais.

Quando vale ligar speculative decoding no vLLM

Is Speculative Decoding Worth It? Profiling vLLM on NVIDIA Blackwell

Speculative decoding acelera a geração quando sobra memória na GPU, o lote é pequeno e a saída é previsível, como JSON ou código.

estudado ✓

Infraestrutura: ver a trilha do tema ≈ 4 min de leitura nível ●●●○○ Akamai Assistir (15:17)

Depois deste talk você consegue decidir se speculative decoding compensa em uma carga de trabalho, olhando tipo de saída, memória livre, contexto e concorrência

Em 3 frases

Um modelo pequeno (draft model) chuta de 3 a 5 tokens e o modelo grande confere todos em uma única passada, então a resposta final sai igual e mais rápida.

Na demo com vLLM em uma GPU NVIDIA Blackwell, a saída estruturada ficou 1,6 vez mais rápida com alta taxa de aceitação, e a escrita criativa teve aceitação bem menor.

O ganho cai quando a GPU já está cheia de requisições, quando o prompt é longo (como em RAG) ou quando o texto pede variedade.

Um modelo pequeno chuta, o grande confere

A inferência tem duas fases. No prefill o modelo lê o prompt e monta o KV cache uma única vez. No decode ele escreve um token por vez, e cada token custa uma passada (forward pass) no modelo grande. Com speculative decoding (decodificação especulativa), um modelo menor propõe de 3 a 5 tokens por ciclo. O modelo alvo aprova ou rejeita todos em uma passada e recalcula os rejeitados. Por isso a qualidade da saída continua a do modelo grande.

O custo é memória para dois modelos

Você hospeda dois modelos e precisa de espaço para o KV cache dos dois. Na demo, o modelo base ocupou cerca de 16 GB de pesos e o draft model 2,5 GB, o que deixou espaço para cache. A palestrante recomenda um draft model de 10 a 50 vezes menor que o alvo, com o mesmo tokenizer e de preferência da mesma família de modelos.

Saída estruturada ganha 1,6 vez de velocidade

A demo roda as duas configurações lado a lado no vLLM. Na tarefa de saída estruturada, a versão especulativa gerou 1,6 vez mais rápido e produziu mais tokens por segundo (throughput, vazão). A métrica que explica o ganho é a taxa de aceitação: tokens aceitos pelo modelo alvo divididos pelo total proposto pelo draft model.

Texto criativo derruba a taxa de aceitação

Na aba de escrita criativa, com temperatura alta, a taxa de aceitação cai bastante. Quanto mais variado o próximo token, menos o modelo pequeno acerta o que o grande escreveria. Poesia e brainstorming ganham pouco. Código, JSON e SQL ganham mais.

Muita adoção, pouca escala

Segundo a pesquisa citada, de 80% a 90% das empresas dizem ter implantado IA ou agentes, mas menos de um terço escalou ou vê impacto de negócio. A causa apontada são pilotos (POCs) em ambientes pequenos que nunca viram fluxo de ponta a ponta.

00:40 Adoção é alta, mas menos de um terço escalou.

Horizon 2 versus Horizon 3

A pesquisa põe as empresas numa escala de maturidade. A maioria está no Horizon 2, com agentes guiados e validados por humanos em tarefas do ciclo de desenvolvimento. Poucas chegaram ao Horizon 3, com fluxo automatizado de ponta a ponta e supervisão humana.

Três fatores: processo, ferramenta e gente

Quem escala redesenha o fluxo inteiro em vez de encaixar agentes no processo antigo. Também cuida de agentes, harnesses e camadas de contexto. O fator mais ignorado são as pessoas, porque as fronteiras entre engenheiro, produto e design estão se apagando.

Codar nunca foi o gargalo

O palestrante pede para olhar as métricas reais: tempo mediano de revisão de PR, tempo para reproduzir bugs, docs desatualizadas, testes. Para ele, o tempo entre código escrito e produção (métrica DORA) supera o de escrever a mudança. Por isso a fábrica precisa de coesão entre times, não só de um agente que programa.

Comece estreito: triagem de incidentes

O agente lê um alerta do Sentry, puxa traces e contexto e posta no Slack. Engenheiros revisam e decidem. Cada diagnóstico correto aumenta a confiança do time. Só depois de ter dono e monitoramento em cada etapa vale fechar o ciclo e ligar a saída ao sinal de entrada.

Três princípios da fábrica

Agnóstica de modelo, para escolher o mais barato que resolve cada tarefa. Implantação soberana, do gerenciado ao isolado da rede (airgapped). Integrada ao ciclo de desenvolvimento inteiro, para que docs, código e testes se informem. Fraqueza em um pilar enfraquece o sistema todo.

Mais 2 ideias deste talk

Oito pilares de agent readiness

Validação (linters, formatadores), build documentado, feedback loops com testes, docs como AGENTS.md, ambientes reproduzíveis, código modular, observabilidade e varredura de segurança. A tese é que preparar o terreno ajuda agentes e humanos igualmente.

Meça resultado, não token

Rankings de tokens e linhas de código são manipuláveis: quem é medido por token gasta token. Palmie propõe tempo do sinal à produção, contagem de intervenções humanas, tempo mediano de reparo, vida útil do código e custo por PR.

Autonomia, automação e qualidade

Autonomia mede quantas vezes um humano precisa corrigir o agente. Automação mede quanto o agente pode rodar sem revisão direta. Qualidade é o resultado para o usuário. A ordem proposta é subir autonomia, depois automação, sempre com a qualidade constante.

O ganho final é qualidade, não só velocidade

Para Knox, a maioria vê a fábrica como forma de entregar mais rápido, aceitando um pouco de lixo. Ele defende que o backlog (fila de pendências) some e sobra capacidade para testes, refatorações e correções. Por isso a qualidade deveria subir depois da transição.

Ciclo interno, externo e meta

O ciclo interno roda barato e o tempo todo, enquanto o agente prepara o PR, e melhora a autonomia. O externo roda checagens caras uma vez, quando o PR sobe, como QA agêntico e teste de mutação. O meta fica fora do desenvolvimento, lê logs, PRs e feedback, e realimenta os outros dois.

Mais 2 ideias deste talk

Por que harness engineering é difícil

Knox aponta três motivos. O campo muda toda semana e o time vira pesquisador. O trabalho não é planejável e compete com o prazo das funcionalidades. Os sinais úteis ficam presos em logs locais e na cabeça das pessoas.

Três camadas, nesta ordem

Primeiro o control plane: issues, revisão no PR e distribuição de skills, para que todo contato com o agente fique registrado. Depois deixar a pilha pronta para agentes (CLI, APIs, logs, ambiente de execução). Por fim os ciclos de melhoria, onde ele diz que o time gasta mais tempo.

analogia

Mutation testing (teste de mutação). Mutation testing é como um professor que coloca erros de propósito numa prova já corrigida para ver se o corretor percebe cada um deles.

  1. Testes automáticos são pequenos programas que conferem se o código faz o que deveria. Mas ninguém confere se os próprios testes são bons.
  2. O teste de mutação (mutation testing) cria cópias do código com um defeito pequeno de propósito, como trocar um sinal de maior por menor ou apagar uma linha.
  3. Cada cópia defeituosa se chama mutante. A ferramenta roda todos os testes contra cada mutante.
  4. Se algum teste falha, o mutante foi pego e o teste cumpriu seu papel. Se todos passam, existe um buraco na suíte de testes, porque um erro real passaria despercebido.
  5. A porcentagem de mutantes pegos mede a qualidade dos testes. Como o processo é caro, Knox sugere rodá-lo uma vez no ciclo externo, quando o PR (pedido de alteração) sobe.

Multi-tenancy (vários clientes isolados no mesmo sistema). Multi-tenancy é como um prédio de escritórios com várias empresas, onde todas dividem o mesmo elevador e a mesma portaria, mas cada uma só abre a própria sala com o crachá dela.

Mesma interface para modelo e agente

A Interactions API usa o mesmo formato de chamada para um modelo Gemini e para um agente. Você passa um modelo ou agente, uma entrada (texto ou multimodal) e ferramentas ou ambiente. O estado da conversa pode ficar no servidor: no turno seguinte você manda só o ID da interação anterior. Tarefas lentas, como gerar vídeo, rodam em segundo plano e você consulta depois.

De turnos user/model para uma linha do tempo de steps

Nas APIs tradicionais, o resultado de uma função volta num turno com papel de usuário, embora venha do ambiente. Schmid defende trocar os turnos por uma linha do tempo de steps (passos), em que cada ação ou geração tem seu próprio tipo. O resultado de função vira function result, e novos recursos entram sem remendos.

Cada agente ganha um sandbox gerenciado e persistente

No campo environment, a chamada pede um sandbox na nuvem. Ali o agente roda código, cria arquivos, instala dependências e chama APIs, sem que você cuide de infraestrutura. O ambiente persiste entre interações e pode ser compartilhado: vários agentes trabalham no mesmo sistema de arquivos ou subagentes retomam o trabalho de outro.

Em 3 frases

Dor Sasson, CEO da Stigg, diz que as crises de preço de abril de 2026 em Anthropic, OpenAI e GitHub foram falhas de infraestrutura, porque o uso era checado só depois da fatura.

Ele propõe verificar permissões de forma síncrona antes de gastar tokens e conciliar o gasto de forma assíncrona depois, com ideias de banco: reserva e liquidação, partida dobrada, ordem de créditos e tetos de gasto.

O talk fecha com quatro padrões para vender IA em escala e pede um 'momento Stripe' para o setor, mas o palestrante vende justamente esse tipo de infraestrutura.

Checar antes, liquidar depois

Hoje muitos times registram o uso depois da inferência e só então conferem limite e cobrança. Sasson defende o caminho inverso: a checagem de direito de uso roda no caminho crítico da requisição, e o acerto de contas acontece depois, de forma assíncrona. Ele compara com o caixa eletrônico, que valida o saque antes de entregar o dinheiro.

Crises de preço eram problema de infraestrutura

Em abril, a Anthropic cortou agentes de terceiros como o OpenClaw dos planos de assinatura, a OpenAI mudou o preço do tier Pro e o GitHub encerrou o acesso gratuito ao Copilot. Para o palestrante, a causa comum foi não conseguir separar quem usa API de quem usa assinatura, nem limitar o gasto antes da fatura.

Três traços da arquitetura da OpenAI

Sasson cita um texto da equipe de financial engineering da OpenAI, de fevereiro. Ele extrai três pontos: a avaliação é única e síncrona, a prioridade é determinística (as regras são conhecidas de antemão) e o sistema é financeiro, não só de cobrança, porque decide antes de qualquer fatura.

Mais 2 ideias deste talk

Concorrência e origem dos créditos

Se 10 mil agentes puxam do mesmo saldo ao mesmo tempo, o saldo visível engana e ocorre gasto duplicado (double spend). Bancos resolvem com reserva (hold), liquidação, idempotência e partida dobrada. Créditos também vêm de fontes diferentes, e é preciso definir qual é consumido primeiro, em vez de usar um único inteiro no banco.

Quatro padrões para vender IA em escala

Os padrões são: reservar antes da inferência e liquidar o real depois; manter o medidor e o ledger (livro-razão) dentro da própria VPC; checar saldo durante o trabalho de agentes, cujo custo não se conhece de antemão; e dar visibilidade de gasto por modelo, equipe, usuário e agente para CFO e CIO.

Simule reserva e liquidação de créditos

Você precisa de: Python 3 ou uma planilha

  1. Crie uma conta com 100 créditos e uma função reservar(valor) que desconta do saldo disponível.
  2. Faça 5 chamadas que reservam 30 créditos cada e veja quantas passam.
  3. Escreva liquidar(reserva, custo_real) que devolve a diferença ao saldo.
  4. Rode de novo com custos reais menores que o reservado e confira o saldo final.

Deu certo se: Só três reservas passam, não há gasto duplicado e o saldo final bate com 100 menos a soma dos custos reais.

O que fazer com isso

  • Cheque limite e saldo antes de cada chamada ao modelo no seu produto ou automação, e registre o consumo real depois.
  • Para agentes cujo custo é imprevisível, reserve um orçamento por tarefa e concilie o gasto real ao final.
  • Defina tetos de gasto por equipe, usuário e agente nas contas de API que sua empresa usa, para um grupo pequeno não esgotar o contrato inteiro.
  • Defina a ordem de consumo dos créditos (promocionais antes dos comprados, por exemplo) e documente a regra.

Depois deste talk você consegue checar se um deploy fora do banco pode derrubá-lo e desenhar uma regra de back pressure e um fluxo seguro de mudança de schema por agentes

Em 3 frases

Ben Dicken, da PlanetScale, defende que dá para entregar rápido sem derrubar o banco, se o sistema tiver isolamento, redundância, sharding, back pressure e componentes desacoplados.

Agentes de IA multiplicam o tráfego e também podem operar a infraestrutura: eles desenham um esquema de sharding a partir de um arquivo JSON e mudam o schema por meio de branches e deploy requests.

A conclusão é que ferramentas feitas para desenvolvedores humanos, como CLI, API, branching e revert com um clique, servem como primitivas seguras para agentes.

Isolamento limita o estrago de um deploy ruim

O data plane (onde moram os dados críticos) fica separado de control plane, observabilidade, analytics, apps e MCPs. Esses outros componentes recebem deploys com mais frequência e falham mais. Um deploy ruim no control plane não pode impedir o acesso ao banco.

Em escala, falha rara vira rotina semanal

Com um servidor de banco, uma falha acontece a cada alguns anos. Com milhares de servidores, vira falha semanal ou mensal. Por isso o padrão é ter um nó primário e réplicas em outros data centers ou zonas de disponibilidade, prontas para assumir.

Sharding espalha dados, e cada shard ainda tem réplicas

Um único nó funciona com 10 GB, mas não com terabytes. O sharding divide dados e consultas entre vários servidores, atrás de um proxy (VTGate). Cada shard mantém primário e réplicas, então se recupera sozinho. A PlanetScale usa Vitess para MySQL e Neki para Postgres.

Mais 2 ideias deste talk

VSchema em JSON deixa o agente propor o sharding

O Vitess é complexo por dentro, mas a configuração de sharding é um arquivo JSON chamado VSchema, no qual se define a coluna de shard e o método. Como agentes lidam bem com texto e JSON, o desenvolvedor passa o schema do banco e pede um protótipo de VSchema. Depois a plataforma aplica via deploy, API ou CLI.

Traffic Control aplica back pressure por orçamento

O recurso Traffic Control etiqueta o tráfego que chega ao banco e define orçamentos de recursos (CPU, processos de backend) por segmento. Ao estourar o orçamento, o sistema avisa o cliente ou mata as consultas. Perde-se parte do tráfego, mas a aplicação inteira não cai.

analogia

Vitess e VSchema (Sistema de sharding para MySQL e seu arquivo JSON de configuração). Vitess com VSchema é como uma agência dos correios que separa as cartas por CEP, seguindo uma tabela simples que diz qual carteiro atende cada bairro.

  1. Quando um banco de dados fica grande demais para um só computador, você divide os dados entre vários servidores. Cada pedaço se chama shard (fatia).
  2. O Vitess é um software livre (open source) que faz essa divisão para o MySQL, um banco de dados muito usado. Cada shard continua sendo um banco MySQL comum.
  3. Na frente das fatias fica o VTGate, um intermediário (proxy). Ele lê cada consulta SQL, descobre em qual shard está o dado e encaminha o pedido para lá.
  4. Para dizer como dividir, você escreve o VSchema, um arquivo JSON (texto organizado em campos e valores). Nele você escolhe a coluna que define a fatia, o método de divisão e quais tabelas ficam em quais shards.
  5. Agentes de IA lidam bem com JSON. Você entrega o schema (a estrutura das tabelas) e pede um rascunho de VSchema. Depois a plataforma aplica a mudança por deploy, API ou linha de comando (CLI).

experimente · 35 min

Mudança de schema por agente, com reversão

Você precisa de: SQLite ou Postgres local e Claude Code ou ChatGPT

  1. Crie um banco de teste com duas tabelas e alguns dados.
  2. Peça ao agente uma migração que adiciona uma coluna, em um arquivo .sql, sem executá-la.
  3. Revise o arquivo e escreva a migração inversa que desfaz a mudança.
  4. Rode a migração em uma cópia do banco, confira o resultado e rode a inversa.

Deu certo se: Você aplicou e reverteu a mudança em uma cópia e os dados originais voltaram idênticos.

O que fazer com isso

  • Liste os componentes do seu sistema e cheque se o deploy de um deles (painel interno, analytics, MCP) pode derrubar o acesso ao banco.
  • Defina o que acontece quando o banco passa do limite de CPU ou conexões. Se a resposta é cair, desenhe uma regra de recusa de parte do tráfego.
  • Antes de deixar um agente alterar o banco, exija um fluxo com branch de schema, revisão humana e reversão pronta.
  • Ao desenhar ferramentas para agentes, exponha configuração em arquivos simples (JSON) e comandos de CLI ou API que eles consigam usar.
